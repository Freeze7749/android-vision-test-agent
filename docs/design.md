# Android Vision Test Agent 设计方案

日期：2026-11-04。状态：待确认，尚未创建任何代码或安装任何东西。

## 1. 为什么做
Zongyuan Chi 是 Android QA 工程师，正在求职 QA 和偏 AI 的岗位，简历已有日志分析项目 Android Bug Triage Agent。这个新项目要给简历增加一个**一眼能看懂、能现场演示**的作品，并且要能在面试中讲清每个部分，所以代码保持简单。

一句话：用自然语言写测试用例，本地模型看着模拟器屏幕一步步操作并判断通过与否，失败时生成带截图和日志的缺陷报告。

## 2. 目标
1. 用自然语言写的测试用例，能在 Android 模拟器上自动执行。
2. 全程用本地模型，不花 API 费用，截图和日志不离开本机。
3. 判定失败时，生成可填入 Jira 的报告，包含每一步截图和 logcat，并调用 Android Bug Triage Agent 分析日志。
4. 用一个埋了已知 bug 的小 App 测量真实指标，结果写进 README。
5. README 有一段真实录制的 GIF。

## 3. 不做的事
- 不支持 iOS、真机农场或多设备并行。
- 不做 Web 界面。
- 不训练模型。
- 不追求替代 Espresso、Maestro 这类成熟工具。类似的 AI 测试工具已经存在，所以 README 不宣称“首创”，卖点是本地运行和公开可复现的指标。

## 4. 算失败的情况（即使代码能跑）
- 指标靠挑选用例或事后调整得来。
- 只会走成功路径，发现不了 bug，或者在没有 bug 的 App 上频繁误报。
- GIF 是剪辑或摆拍的，不能复现。
- 用户在面试中讲不清某个模块。

## 5. 工作流程
```
测试用例（一句话或 YAML）
   ↓
循环，最多 N 步：
   截图 + UI 元素列表（adb）
   → 本地模型决定下一步：点第几个元素 / 输入 / 滑动 / 返回 / 结束并判定
   → 程序校验动作，通过 adb 执行，保存这一步的记录
   ↓
判定：通过 / 失败 / 无法判断
   ↓ 失败时
抓 logcat → Triage Agent 分析 → 生成报告（步骤截图 + 日志引用）
```

### 关键设计决定（均为我的建议，待你确认）
| 决定 | 选择 | 理由 |
|---|---|---|
| 怎么点屏幕 | 从 `uiautomator dump` 得到带编号的元素列表，模型只选编号 | 小模型猜坐标不准，选编号稳定，也容易解释 |
| 截图的作用 | 判断界面状态和视觉问题 | 文字错位、颜色异常这类问题只有截图能看到 |
| 判定防幻觉 | 判定必须指明依据的元素或步骤，程序核对它确实存在 | 延续第一个项目“引用必须可验证”的思路，也是面试亮点 |
| 动作安全 | 程序只执行固定的几种动作，模型不能运行任意 shell 命令 | 屏幕上的文字是不可信数据，不能当指令 |
| 和 Triage Agent 的关系 | 作为依赖调用其 `triage` 功能，没有它时跳过分析 | 两个项目串成完整链路，但互不绑定 |
| 语言 | Agent 用 Python；被测 App 用 Kotlin，尽量写小 | Python 与第一个项目一致 |
| 模型 | 通过 Ollama 调用，小实验比较 `qwen3.5:4b`（约 3.3–4GB）和 `gemma3:4b`（3.4GB），用得好且放得下的那个 | 显存只有 8GB。两者都支持图片输入，许可证要在写进 README 前核对 |
| 存放 | 新的独立仓库 `F:\Projects\android-vision-test-agent`，SDK 和模拟器放 F 盘 | C 盘只剩约 33GB |

## 6. 被测 App 和评估
**App：** 自己写一个小的笔记类 App（列表、新建、编辑、搜索、设置页）。每个 bug 用一个开关控制，所以同一个 App 可以运行“无 bug”和“开启某个 bug”两种状态。数据全部是自己生成的。

**埋入的 bug 类型：** 崩溃、保存不生效、按钮缺失、文字错误、搜索结果错误、无响应，以及只有截图才能看出的视觉问题（如文字被遮挡）。

**数据划分：** 开发组 bug 用来调提示词，测试组 bug 留到最后只跑一次，沿用第一个项目的做法，并公开记录调整过程。

**报告的指标：**
- bug 检出率：开启 bug 时判定失败的比例。
- 误报率：无 bug 时判定失败的比例。
- 用例完成率，以及“无法判断”的比例。
- 每个用例的平均步数和耗时。
- 对比基线：同一模型只给元素列表、不给截图，用来回答“视觉到底有没有帮助”。结果可能是没帮助，那也如实写。

**局限（README 要写明）：** App 和 bug 都由本项目自己编写，用例数量小，结果不代表真实产品上的表现；只在模拟器上运行过，不是真机。

用例和 bug 的具体数量等小实验测出单步耗时后再定，避免一次评估跑太久。

## 7. 先做小实验再正式开工
模型能否看准手机屏幕是最大风险，所以先做一次性小实验。它不进正式代码，也不用写测试。

- **内容：** 在模拟器的系统设置 App 上，给 10 条具体指令（如“打开网络设置”），看模型能否选对元素；再用几张截图问它界面状态。
- **继续的标准（我的建议）：** 10 条至少选对 8 条，单步不超过约 1 分钟。
- **不达标时：** 先换另一个模型。还不行就改成主要靠元素列表，只在判定环节用截图。如果仍然不可行，我会如实告诉你，再决定是否换项目。
